# 책 분석 품질 평가 방법

이 평가는 기능이 실행되는지와 설명이 옳은지를 나누어 측정한다. 현재 네 작품은 개발에 사용한 **파일럿 자료**다. 새 작품에 대한 일반 성능을 입증하는 독립 시험 자료는 아니다. 아래 합격선은 프로젝트의 초기 목표이며 공인 기준이 아니다.

## 평가 묶음과 기준 고정

- 최신 파일럿: `reading-playtest/evaluation/pilot-2026-11-21-v2/`.
- `snapshot.json`: Supabase에서 읽은 네 작품의 원문·현재 분석과 SHA-256. DB를 수정하거나 새 AI 분석을 요청하지 않는다. 원문·분석이 바뀌면 새 폴더로 다시 추출한다.
- `units.json`: 실제 화면에서 쓰는 분석의 평가 단위와 문제를 고정한 목록. 사용하지 않는 이전 분석이나 캐릭터 외형 설명은 내용 평가에서 제외한다. 논문의 수치 비교도 별도 단위로 포함한다.
- 문장 단위로 자동 분리하되, 한 단위에 독립된 주장이 여러 개 섞였는지 **채점 전에** 검토한다. 필요하면 추출 규칙을 수정해 새 묶음을 만들고 단위를 고정한다. 낮은 점수를 받은 뒤 단위를 합치거나 지우면 안 된다.
- `gold-draft.json`: 원문 위치·필수 내용·허용할 수 없는 설명을 적은 장르별 기준 24개. 개발자가 작성한 초안으로, 두 평가자가 원문을 보고 승인하기 전에는 확정 정답표가 아니다. 정답표를 AI 출력과 같게 고쳐 점수를 높이지 않는다.
- 시의 문단 번호는 0부터 시작한다. 「서시」의 실제 1~9행은 ordinal 0~8이며 이후 출처 문단은 시의 행이 아니다.

## 두 평가자가 따로 채점하기

두 사람은 서로의 표와 점수를 보지 않고 같은 원문·기준으로 평가한다. 기능을 만든 담당자의 단독 채점은 독립 검증이라고 발표하지 않는다. 가능하면 진행자 한 명이 초안·검토본의 묶음 이름을 무작위로 바꿔 배포하고 생성 단계와 작성자를 숨긴다. 현재 파일 자체가 블라인드 검증 완료를 의미하지 않는다.

1. `coverage-A.csv`, `coverage-B.csv`: 기준의 `source_ordinals`에 있는 원문을 확인하고 `criterion_approved`를 1/0으로 표시한다. 원문만으로 판단할 수 없거나 표현이 모호하면 0과 이유를 남긴다. 승인되지 않은 기준은 합의·수정 후 새 기준 버전으로 고정한다.
2. `claims-A.csv`, `claims-B.csv`: `correct`, `supported`, `critical_error`를 각각 1/0으로 채운다. 빈칸은 미검토이며 정답이나 제외 대상으로 계산하지 않는다. `note`에 판단 이유와 필요한 원문 위치를 적는다.
3. `questions-A.csv`, `questions-B.csv`: `single_best_answer`는 정답이 하나이고 지정한 정답이 맞으면 1, 아니면 0이다. `explanations_correct_count`에는 올바른 해설 개수를 적는다. 5지선다는 보기 5개, 카드 연결은 해당 칸에 대한 해설 1개를 분모로 삼는다. 정답 선택의 이유와 오답 배제 이유를 모두 확인한다. `critical_error`도 1/0으로 채운다.
4. 기준별로 분석의 어느 `unit_id`가 설명하는지 찾아 `matched_unit_ids`에 쉼표로 적고 `covered`를 1/0으로 채운다. 단어가 언급되기만 한 경우는 포함으로 인정하지 않는다. 틀린 설명도 포함으로 인정하지 않는다.

`correct=1`: 원문과 모순되지 않고, 해석이라면 문맥 근거를 제시하며 가능한 해석의 범위를 지킨다. 생활 비유는 원문 사실처럼 제시하지 않고 비유의 한계를 밝혀야 한다. 시의 상징을 유일한 뜻으로 단정하지 않았다고 해서 모호한 답으로 감점하지 않는다.

`supported=1`: **서비스가 붙인 근거**로 해당 주장 전체를 설명할 수 있다. 인용 문구가 정확히 복사됐더라도 의미가 뒷받침되지 않으면 0이다. 원문 다른 곳에 근거가 있어도 첨부 근거가 없거나 부적합하면 내용 정확도는 1, 근거 적합도는 0일 수 있다. 기존 소설 관계도의 근거는 실제 API처럼 저장된 ordinal의 문단을 붙여 평가한다. 인물 속성에 근거가 없으면 임의로 만들어 붙이지 않는다.

`critical_error=1`: 정답·오답 뒤집기, 연구 결론이나 사건 순서 반전, 잘못된 수치로 반대 결론 유도, Ready/Blocked 혼동처럼 사용자의 핵심 이해를 잘못 이끄는 오류다. 심각도는 채점 전에 예시로 맞춘다.

## 계산과 공개 기준

| 지표 | 계산 | 초기 목표 |
|---|---|---|
| 내용 정확도 | correct=1인 설명 단위 / 전체 설명 단위 | 작품별 95% 이상 |
| 근거 적합도 | supported=1인 설명 단위 / 전체 설명 단위 | 작품별 95% 이상 |
| 핵심 내용 포함률 | 올바르게 설명한 승인 기준 / 전체 승인 기준 | 작품별 90% 이상 |
| 정답 명확성 | 정답이 하나이고 지정 정답이 맞는 문제 / 전체 문제 | 공개 문제 100% |
| 해설 정확도 | 올바른 해설 / 전체 평가 대상 해설 | 작품별 95% 이상 |
| 범위·정답 노출 | 미독·부분 진도·완독 경계와 풀이 전 응답에서 잘못 공개된 항목 수 | 0건 |

비율과 함께 반드시 `정확한 개수/전체 개수`를 표시한다. 작품별 결과를 먼저 보고 전체 합산은 참고로 사용한다. 문장이 많은 전공서적의 점수로 소설의 낮은 점수를 가리지 않는다. 일부만 채점된 비율은 임시 수치이며 합격 판정에 사용하지 않는다. 심각한 오류가 하나라도 있으면 평균과 관계없이 공개 보류다.

채점 프로그램은 A/B 점수를 각각 계산하고, 둘 다 채운 같은 항목 중 같은 판단의 비율과 불일치 목록을 출력한다. 불일치에 대해서는 원래 A/B 표를 보존한 채 별도 합의 기록(항목 ID·최종 판단·근거·결정자)을 작성한다. 합의 전 점수를 단순 평균하여 최종 품질이라고 발표하지 않는다. 프로그램은 자동 출시 승인을 하지 않는다.

## 자동 검사가 말해 주는 범위

`automatic-checks.csv`는 인용 문자열의 원문 포함 여부, 시 문제 형식, 풀이 전 응답의 정답·해설 필드 제외, 장르 분석 함수의 미독·중간·완독 경계를 검사한다. **내용 정확도나 근거 의미를 판정하지 않는다.** 기존 소설은 해당 장르 함수 경계 검사 대상이 아니므로 별도 HTTP·화면 검증이 필요하다. 고정된 세 경계를 통과했다고 모든 가능한 진도를 검사한 것은 아니다.

이전 Supabase 전용 검증 책의 브라우저 검사에서는 잠금·오답 미지급·정답 연출·캐릭터 반복 동작·중복 지급 방지를 확인했다. 해당 기능 결과를 이번 자동 의미 평가 점수로 합산하지 않는다. 새 스크립트는 읽기 전용이며 사용자 독서 진도를 변경하지 않는다.

## AI 초안과 검토본 비교

- `raw-poetry/`에는 보존된 Gemini 원본 JSON에서 만든 별도의 「서시」 설명·문제 채점표가 있다. 원본 파일 해시도 남긴다. 같은 시의 현재 검토본과 각각 채점하고, 수정한 항목의 오류가 줄었는지 비교한다.
- 소설·전공서적·논문은 현재 추출 묶음에서 수정 전 전체 초안이 입증되지 않았다. 현재 결과를 과거 AI 초안이라고 복원하거나, 기억만으로 수정 전 점수를 채우지 않는다.
- 「서시」도 개발 중 재시도한 뒤 보존된 초안이다. 첫 호출 성공률이나 무작위 새 작품 성능을 뜻하지 않는다. 과거 전체 요청 수와 실패 로그가 완전하지 않아 당시 생성 성공률도 계산하지 않는다.
- 앞으로는 원문 해시·프롬프트/스키마 버전·모델·생성 설정·요청 시작/종료·실패·수동 수정 전 결과를 보존한다. 성공 사례만 남기지 않는다. API 키는 기록하지 않는다.

## 새 작품 20편으로 일반 성능 평가하기

장르별 새 작품 5편을 확보하고 작품 단위로 개발 자료와 분리한다. 같은 작품의 다른 부분을 새 작품처럼 넣지 않는다. 생성 전에 두 평가자가 기준표를 확정하고 모델·프롬프트 버전을 고정한다. 평가 출력은 수동 수정하지 않은 상태로 채점한다. 실패한 생성도 별도로 전수 기록한다. 이를 현재 네 작품의 검토 후 점수와 섞지 않는다.

생성 성공률(전체 시도 중 유효 분석 완성), 재시도 횟수, 생성 시간과 사용 중 조회 지연도 별도 측정할 수 있다. 캐시 조회와 AI 생성 시간을 섞지 말고, 서버 최초 실행과 예열 후 결과를 구분한다. 현재 자료만으로 해당 수치를 소급하여 만들지는 않는다.

## 실행

이 저장소 루트에서 팀 Supabase 테스트 프로젝트 설정을 사용한다. 출력 폴더는 Git에서 제외되며 새 이름을 사용한다.

```bash
python -m backend.scripts.evaluate_reading_quality --output evaluation-runs/pilot
python -m backend.scripts.score_reading_quality evaluation-runs/pilot --prepare
python -m backend.scripts.score_reading_quality evaluation-runs/pilot
```

이 명령의 네 작품 ID는 기존 개발 카탈로그 기준이다. 빈 DB에는 해당 작품을 담당자가 먼저 등록해야 한다. 다른 작품을 평가하려면 대상 ID와 원문 기반 기준을 함께 변경한다.

원본 초안·기존 평가 스냅샷·브라우저 프로필은 이 공개 저장소에 포함하지 않았다. 위 문서의 기존 파일럿 경로와 raw-poetry는 원본 개발 환경의 기록을 설명한다. 새로운 평가 실행에서는 이번에 확보한 원문과 초안만 사용하고 자료가 없는 과거 점수를 복원하지 않는다.
